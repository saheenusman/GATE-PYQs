# 2008 CS Q77: Which instruction can fill the branch delay slot

## Question

The following code is to run on a pipelined processor with one branch delay slot:

```
I1: ADD R2 <- R7 + R8
I2: SUB R4 <- R5 - R6
I3: ADD R1 <- R2 + R3
I4: STORE Memory[R4] <- R1
    BRANCH to Label if R1 == 0
```

Which of the instructions I1, I2, I3 or I4 can legitimately occupy the delay slot without any other program modification?

- (A) I1
- (B) I2
- (C) I3
- (D) I4

<details class="success" markdown="1">
<summary>Answer</summary>

**B** (official key; see the Solution: disputed)

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

**Status: disputed.** The official key is (B), I2. I get (D), I4. Both views follow.

**The rule.** An instruction moved into the delay slot executes **after** the branch is issued (and always), so it must not change what the branch reads, and nothing between its old and new place may depend on it, in either direction.

| Candidate | Why it cannot be moved after the branch (or why it can) |
|---|---|
| I1 (`R2 = R7 + R8`) | I3 reads `R2`. Moving I1 later would make I3 use the old `R2`. **No.** |
| I2 (`R4 = R5 - R6`) | I4 reads `R4` (the store address). Moving I2 after I4 would make the store use the old `R4`. **No.** |
| I3 (`R1 = R2 + R3`) | The branch reads `R1` and I4 stores `R1`. **No.** |
| I4 (`Mem[R4] = R1`) | It is the instruction just before the branch. The branch does not depend on it (it reads `R1` only), and it is executed either way. **Yes.** |

So only **I4** can legitimately fill the delay slot: (D).

**Key's view.** The key's (B) says I2 can fill the slot. But I4 uses `R4`, and executing I2 after I4 would change the address the store uses. Placing I2 in the slot would only be legal if I4 were also moved or `R4` were not used by it, which the question excludes ("without any other program modification"). I record (B) and mark the question disputed.

**Key idea:** a delay-slot candidate must be independent of the branch condition and of every instruction it jumps over.

</details>
