# 2022 CS Q55: Aggregating subnets with CIDR prefixes

## Question

Consider routing table of an organization's router shown below:

| Subnet Number | Subnet Mask | Next Hop |
| --- | --- | --- |
| 12.20.164.0 | 255.255.252.0 | R1 |
| 12.20.170.0 | 255.255.254.0 | R2 |
| 12.20.168.0 | 255.255.254.0 | Interface 0 |
| 12.20.166.0 | 255.255.254.0 | Interface 1 |
| default | | R3 |

Which of the following prefixes in CIDR notation can be collectively used to correctly aggregate all of the subnets in the routing table?

- (A) 12.20.164.0/20
- (B) 12.20.164.0/22
- (C) 12.20.164.0/21
- (D) 12.20.168.0/22

<details class="success" markdown="1">
<summary>Answer</summary>

**B and D**

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

**Third octet ranges.**
- `12.20.164.0/22` (mask 252): 164 to 167.
- `12.20.166.0/23` (mask 254): 166 to 167, inside the first entry.
- `12.20.168.0/23`: 168 to 169.
- `12.20.170.0/23`: 170 to 171.

So the subnets together cover third octets 164 to 171 (two blocks of four).

**Aggregates.**
- `12.20.164.0/22` covers 164 to 167. ✓ (B)
- `12.20.168.0/22` covers 168 to 171, which contains the 168.0/23 and 170.0/23 subnets. ✓ (D)

Together, B and D cover exactly the subnets.

**Why the others fail:**
- (A) `12.20.164.0/20` is not a valid prefix. A /20 must start at a multiple of 16 in the third octet, and 164 is not. The valid /20 block is 160 to 175, which also covers addresses that are not in the table.
- (C) `12.20.164.0/21` is not valid either. A /21 block starts at a multiple of 8, and 164 is not. The valid block 160 to 167 would cover addresses outside the table.

**Code check:** Python's `ipaddress` module accepted `/22` prefixes at 164.0 and 168.0 and rejected the /20 and /21 prefixes with base 164.0 (host bits set).

**Key idea:** a CIDR prefix must start on a block boundary; two adjacent /22 blocks aggregate the four subnets.

</details>
