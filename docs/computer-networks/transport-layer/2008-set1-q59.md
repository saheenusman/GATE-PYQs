# 2008 CS Q59: Behaviour of connect() when the server has not called accept()

## Question

A client process P needs to make a TCP connection to a server process S. Consider the following situation: the server process S executes a `socket()`, a `bind()` and a `listen()` system call in that order, following which it is preempted. Subsequently, the client process P executes a `socket()` system call followed by `connect()` system call to connect to the server process S. The server process has not executed any `accept()` system call. Which one of the following events could take place?

- (A) `connect()` system call returns successfully
- (B) `connect()` system call blocks
- (C) `connect()` system call returns an error
- (D) `connect()` system call results in a core dump

<details class="info" markdown="1">
<summary>Solution</summary>

**Status: disputed.** The supplied key gives no single letter ("B or C ??"). My own derivation points to (A). Both views follow.

**What the kernel does.** After `listen()`, the server's kernel accepts incoming SYNs on its own: it replies with SYN-ACK, receives the client's ACK, and puts the **fully established** connection into the listen queue (the backlog). The server process does **not** need to be running, and `accept()` is only the call that later takes the connection out of that queue.

- So as long as the backlog is not full, the client's three-way handshake completes and **`connect()` returns successfully** (A). This is the normal case in the question.
- (B) and (C) can happen only if the listen queue is **full**: the kernel then ignores new SYNs, the client keeps retransmitting, `connect()` blocks (B), and finally fails with a timeout error (C). The question gives no reason to assume a full queue (the server only called `listen()` once and nobody else is connecting).
- (D) is not something `connect()` does.

"Could take place" asks for something possible, and (A) is the one possible in the described situation. I record the key's "B or C" but mark the question disputed.

**Key idea:** the TCP handshake is completed by the kernel of a listening socket; `accept()` only collects connections that are already established.

</details>
