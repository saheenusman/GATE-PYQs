# 2009 CS Q55: Interpretation of a nested NOT IN query

## Question

**Common data for Questions 55 and 56.** Consider the following relational schema:

`Suppliers(sid: integer, sname: string, city: string, street: string)`

`Parts(pid: integer, pname: string, color: string)`

`Catalog(sid: integer, pid: integer, cost: real)`

(In the paper, `sid` in Suppliers, `pid` in Parts, and the pair `sid, pid` in Catalog are underlined as the keys.)

**Q55.** Consider the following relational query on the above database:

```sql
SELECT S.sname
FROM Suppliers S
WHERE S.sid NOT IN ( SELECT C.sid
                     FROM Catalog C
                     WHERE C.pid NOT IN ( SELECT P.pid
                                          FROM Parts P
                                          WHERE P.color <> 'blue'))
```

Assume that relations corresponding to the above schema are not empty. Which one of the following is the correct interpretation of the above query?

- (A) Find the names of all suppliers who have supplied a non-blue part.
- (B) Find the names of all suppliers who have not supplied a non-blue part.
- (C) Find the names of all suppliers who have supplied only blue parts.
- (D) Find the names of all suppliers who have not supplied only blue parts.

<details class="success" markdown="1">
<summary>Answer</summary>

**A or D** (the supplied key accepts both)

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

**Status: disputed.** The supplied key accepts (A) or (D). Evaluating the query exactly as printed, I find that **none** of the four options matches it. Both follow.

**Reading the query from the inside out** (assuming no NULL colours and that every `Catalog.pid` appears in `Parts`):

1. Innermost: the non-blue parts, `P.color <> 'blue'`.
2. Middle: `C.pid NOT IN (non-blue parts)` keeps the catalog rows for **blue** parts. So the middle query returns the `sid`s of suppliers who have supplied **at least one blue part**.
3. Outer: `S.sid NOT IN (...)` keeps the other suppliers: those who have **not supplied any blue part** (this includes suppliers with no catalog rows at all).

**Checking each option against that:**

| Option | Meaning | Where it differs from the query |
|---|---|---|
| (A) supplied a non-blue part | has a non-blue row | a supplier of one blue and one red part is in (A) but not in the query; a supplier with no rows is in the query but not in (A) |
| (B) not supplied a non-blue part | no non-blue row | a supplier of only blue parts is in (B) but not in the query |
| (C) supplied only blue parts | all rows blue | these suppliers supplied a blue part, so the query **excludes** them: the opposite |
| (D) not supplied only blue parts | not (all rows blue) | a supplier of one blue and one red part is in (D) but not in the query |

**What the key says.** (A) or (D). I could not find a reading of the printed query that matches either, so I record the key's answer and flag the conflict.

**Observation:** if the inner condition were `P.color = 'blue'` instead of `<>`, the query would return suppliers who have not supplied a non-blue part, which is exactly (B). That suggests a possible slip in the printed query, but I cannot confirm this from the paper.

**Code check:** a program built all $512$ possible catalogs for $3$ suppliers and $3$ parts (one red, two blue), ran the query, and compared it with each option. The option's result equalled the query's result in only $64$ cases for (A), $64$ for (B), $27$ for (C) and $125$ for (D), out of $512$, so none matches. With `P.color = 'blue'` in place of `<>`, option (B) matched in all $512$.

**Key idea:** `NOT IN` of `NOT IN` flips twice, but here the inner filter is "non-blue", so the middle query selects the blue-part suppliers, and the outer `NOT IN` excludes them.
