# 2012 CS Q15: HAVING without GROUP BY, and GROUP BY attributes in SELECT

## Question

Which of the following statements are **TRUE** about an SQL query?

- **P:** An SQL query can contain a HAVING clause even if it does not have a GROUP BY clause
- **Q:** An SQL query can contain a HAVING clause only if it has a GROUP BY clause
- **R:** All attributes used in the GROUP BY clause must appear in the SELECT clause
- **S:** Not all attributes used in the GROUP BY clause need to appear in the SELECT clause

Options:

- (A) P and R
- (B) P and S
- (C) Q and R
- (D) Q and S

<details class="success" markdown="1">
<summary>Answer</summary>

**C**

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

**Status: disputed.** The official key is (C), "Q and R". My own analysis gives (B), "P and S". Both follow.

**What I get, statement by statement.**

- **P true.** Standard SQL allows `HAVING` without `GROUP BY`; the whole table is treated as a single group. Example: `SELECT COUNT(*) FROM A HAVING COUNT(*) > 1`.
- **Q false**, because P is true.
- **R false.** The rule runs the other way: every non-aggregated column in `SELECT` must appear in `GROUP BY`. A grouped column can be left out of `SELECT`: `SELECT COUNT(*) FROM A GROUP BY Name` is legal.
- **S true.**

So P and S, which is (B).

**What the key says.** (C) needs Q (HAVING only with GROUP BY) and R (all grouped attributes in SELECT) to be true. I could not find a reading of standard SQL under which either holds. Answer sites that defend the key admit that real engines such as MySQL accept P. I record the official key (C) and flag the conflict.

**Code check:** SQLite 3.53 ran `HAVING` without `GROUP BY` and a `GROUP BY` column left out of `SELECT`, both without error. I did not test another engine.

**Key idea:** `HAVING` filters groups, and with no `GROUP BY` there is exactly one group; `SELECT` must be covered by `GROUP BY`, not the reverse.

</details>
