# 2014 CS1 Q22: Foreign key vs check assertion; foreign key to a composite key

## Question

Given the following statements:

**S1**: A foreign key declaration can always be replaced by an equivalent check assertion in SQL.

**S2**: Given the table `R(a,b,c)` where `a` and `b` together form the primary key, the following is a valid table definition.

```sql
CREATE TABLE S (
  a INTEGER,
  d INTEGER,
  e INTEGER,
  PRIMARY KEY (d),
  FOREIGN KEY (a) references R)
```

Which one of the following statements is **CORRECT**?

- (A) S1 is TRUE and S2 is FALSE.
- (B) Both S1 and S2 are TRUE.
- (C) S1 is FALSE and S2 is TRUE.
- (D) Both S1 and S2 are FALSE.

<details class="success" markdown="1">
<summary>Answer</summary>

**D**

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

**S2 is false.** `FOREIGN KEY (a) references R` with no column list refers to the primary key of `R`, which is the pair $(a,b)$. A foreign key must have as many columns as the key it references, so a single column `a` cannot reference a two-column key.

**Code check:** in SQLite with foreign keys on, the table `S` as written fails on the first insert with `foreign key mismatch - "S" referencing "R"`.

**S1 is false** (as the key has it). A foreign key also carries referential actions (`ON DELETE CASCADE`, `ON UPDATE ...`), which a check assertion does not provide, so it cannot always replace one. I took this from the key and the SQL standard; it is a theory point I could not test in a DBMS. Most DBMSs do not implement `CREATE ASSERTION` at all.

So (D). (A), (B), (C) each claim at least one of them is true.

**Key idea:** a foreign key must match the whole referenced key, and it does more than a check.

</details>
