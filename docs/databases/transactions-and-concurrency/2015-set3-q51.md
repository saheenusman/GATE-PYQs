# 2015 CS3 Q51: Recoverability of a schedule where T1 fails after T2 commits

## Question

Consider the following partial Schedule $S$ involving two transactions $T1$ and $T2$. Only the *read* and the *write* operations have been shown. The *read* operation on data item $P$ is denoted by read($P$) and the *write* operation on data item $P$ is denoted by write($P$).

| Time instance | $T1$ | $T2$ |
|---|---|---|
| 1 | read(A) | |
| 2 | write(A) | |
| 3 | | read(C) |
| 4 | | write(C) |
| 5 | | read(B) |
| 6 | | write(B) |
| 7 | | read(A) |
| 8 | | commit |
| 9 | read(B) | |

Suppose that the transaction $T1$ fails immediately after time instance 9. Which one of the following statements is correct?

- (A) T2 must be aborted and then both T1 and T2 must be re-started to ensure transaction atomicity
- (B) Schedule S is non-recoverable and cannot ensure transaction atomicity
- (C) Only T2 must be aborted and then re-started to ensure transaction atomicity
- (D) Schedule S is recoverable and can ensure atomicity and nothing else needs to be done

<details class="success" markdown="1">
<summary>Answer</summary>

**B**

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

At time 7, $T2$ reads $A$, which $T1$ wrote at time 2 and has **not yet committed**. That is a dirty read: $T2$ depends on $T1$.

$T2$ then **commits at time 8**, before $T1$ has finished.

A schedule is **recoverable** only if a transaction that reads from another commits *after* it. Here $T2$ committed first. When $T1$ fails, its write to $A$ must be undone, but $T2$'s result already used that write, and a committed transaction cannot be rolled back. So the schedule is **non-recoverable**, and atomicity cannot be ensured. Option (B).

- (A) and (C) assume $T2$ can still be aborted, but it has committed.
- (D) is false for the same reason: nothing can repair $T2$ now.

**Code check:** scanning the schedule finds that $T2$ reads from $T1$ and commits at time 8, with no commit of $T1$ before it.

**Key idea:** recoverable means every transaction commits only after the transactions it read from have committed.

</details>
