# 2017 CS1 Q42: Deadlock and starvation with a timestamp-based kill-or-wait rule

## Question

In a database system, unique timestamps are assigned to each transaction using Lamport's logical clock. Let $TS(T_1)$ and $TS(T_2)$ be the timestamps of transactions $T_1$ and $T_2$ respectively. Besides, $T_1$ holds a lock on the resource R, and $T_2$ has requested a conflicting lock on the same resource R. The following algorithm is used to prevent deadlocks in the database system assuming that a killed transaction is restarted with the same timestamp.

```
if TS(T2) < TS(T1) then
    T1 is killed
else T2 waits.
```

Assume any transaction that is not killed terminates eventually. Which of the following is TRUE about the database system that uses the above algorithm to prevent deadlocks?

- (A) The database system is both deadlock-free and starvation-free.
- (B) The database system is deadlock-free, but not starvation-free.
- (C) The database system is starvation-free, but not deadlock-free.
- (D) The database system is neither deadlock-free nor starvation-free.

<details class="success" markdown="1">
<summary>Answer</summary>

**A**

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

**Which scheme this is.** The requester $T_2$ wants a lock held by $T_1$.

- If $T_2$ is **older** ($TS(T_2) < TS(T_1)$), it takes priority: the holder $T_1$ is killed ("wounded").
- If $T_2$ is **younger**, it waits.

This is the **wound-wait** scheme.

**Deadlock-free.** A transaction only ever *waits* for an older one (a younger requester waits for an older holder; an older requester never waits, it kills). So every edge of the wait-for graph goes from a younger to an older transaction. Timestamps are unique and strictly ordered, so no cycle can form.

**Starvation-free.** A killed transaction restarts with the **same** timestamp, so it keeps its age. It can only be killed by an *older* transaction. There are finitely many older transactions, and each terminates (given), so eventually the restarted transaction is the oldest one and can never be killed again.

Both properties hold: **(A)**.

**Why the others fail.** (B) would be right if restarted transactions got a *new, larger* timestamp, since they could then be killed again and again. (C) and (D) deny deadlock freedom, but waiting only ever points from younger to older.

**Status note:** conceptual question; no program to run. My reasoning matches the official key.

**Key idea:** wound-wait is deadlock-free because waits point one way (young to old), and starvation-free because a restarted transaction keeps its original timestamp.

</details>
