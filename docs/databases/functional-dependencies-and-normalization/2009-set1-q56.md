# 2009 CS Q56: Normal form of Suppliers with sid and (sname, city) as keys

## Question

**Common data for Questions 55 and 56** (the schema is given with Q55: `Suppliers(sid, sname, city, street)`, `Parts(pid, pname, color)`, `Catalog(sid, pid, cost)`).

**Q56.** Assume that, in the suppliers relation above, each supplier and each street within a city has a unique name, and (sname, city) forms a candidate key. No other functional dependencies are implied other than those implied by primary and candidate keys. Which one of the following is TRUE about the above schema?

- (A) The schema is in BCNF.
- (B) The schema is in 3NF but not in BCNF.
- (C) The schema is in 2NF but not in 3NF.
- (D) The schema is not in 2NF.

<details class="info" markdown="1">
<summary>Solution</summary>

**Status: disputed.** The supplied key says (B). My own analysis gives (A) BCNF. Both follow.

**What I get (A).** The question says the only functional dependencies are those implied by the primary key and the candidate key. So the dependencies are:

- $sid \to sname, city, street$
- $sname, city \to sid, street$

The candidate keys are $\lbrace sid \rbrace$ and $\lbrace sname, city \rbrace$. In every dependency the left side is a key. That is exactly the definition of **BCNF**: (A). BCNF also implies 3NF and 2NF, so (C) and (D) are false as well.

**What the key says.** (B), "3NF but not BCNF". A schema is in 3NF but not BCNF only when some dependency $X \to A$ has a left side $X$ that is **not** a superkey. The question explicitly says there is no such dependency ("no other functional dependencies are implied"), so I could not find a reading that supports (B). I record the key and flag the conflict.

- (C) and (D) cannot hold when the schema is in BCNF: the only non-key attribute, `street`, depends on the whole of each key, so there is no partial or transitive dependency.

**Code check:** an attribute-closure program on these two dependencies found exactly the candidate keys $\lbrace sid \rbrace$ and $\lbrace sname, city \rbrace$, and found **no** implied nontrivial dependency whose left side is not a superkey, so the schema is in BCNF.

**Key idea:** if every functional dependency has a (super)key on its left side, the schema is in BCNF; 3NF-but-not-BCNF needs a dependency from a non-key.
