# 2020 CS Q51: Reporting all keys in a range from a balanced BST

## Question

In a balanced binary search tree with $n$ elements, what is the worst case time complexity of reporting all elements in range $[a, b]$? Assume that the number of reported elements is $k$.

- (A) $\Theta(\log n)$
- (B) $\Theta(\log n + k)$
- (C) $\Theta(k \log n)$
- (D) $\Theta(n \log k)$

<details class="success" markdown="1">
<summary>Answer</summary>

**B**

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

**Method.**

1. Search for $a$ and for $b$. Each search follows one root-to-leaf path in a balanced tree: $O(\log n)$.
2. The keys in $[a, b]$ lie between those two paths. Walk the tree in inorder between them and output every key found.

**Cost of step 2.** The walk only enters subtrees whose keys all lie in $[a,b]$, plus the nodes on the two search paths. Every node it visits inside a fully-covered subtree is reported, so that part costs $O(k)$. The path nodes cost $O(\log n)$.

$$\text{Total} = O(\log n) + O(k) = \Theta(\log n + k).$$

**It cannot be better.** Printing $k$ keys takes $\Omega(k)$ time, and locating the range takes $\Omega(\log n)$ comparisons in the worst case.

**Why the others fail:**

- **(A)** ignores the output size. Reporting $k$ keys cannot take less than $k$ steps.
- **(C)** is what you get by doing $k$ separate searches from the root. Using the tree structure to move from one key to the next avoids that.
- **(D)** has no justification: the running time does not depend on $n$ beyond the $\log n$ search.

**Key idea:** range reporting is *output-sensitive*: a logarithmic search to find the range, plus time proportional to the number of keys reported.

</details>
