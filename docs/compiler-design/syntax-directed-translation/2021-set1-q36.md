# 2021 CS1 Q36: What the type-checking SDT actions can handle

## Question

Consider the following grammar (that admits a series of declarations, followed by expressions) and the associated syntax directed translation (SDT) actions, given as pseudo-code:

```
P -> D* E*
D -> int ID   {record that ID.lexeme is of type int}
D -> bool ID  {record that ID.lexeme is of type bool}
E -> E1 + E2  {check that E1.type = E2.type = int;
               set E.type := int}
E -> ! E1     {check that E1.type = bool;
               set E.type := bool}
E -> ID       {set E.type := int}
```

With respect to the above grammar, which one of the following choices is correct?

- (A) The actions can be used to correctly type-check any syntactically correct program.
- (B) The actions can be used to type-check syntactically correct integer variable declarations and integer expressions.
- (C) The actions can be used to type-check syntactically correct boolean variable declarations and boolean expressions.
- (D) The actions will lead to an infinite loop.

<details class="success" markdown="1">
<summary>Answer</summary>

**B**

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

The key rule is $E\to ID$: it sets $E.type:=\texttt{int}$ **whatever type the declaration recorded** for the ID (the action never looks it up).

- (B) **Integer declarations and integer expressions work.** `int x` is recorded and `x` gets type int, and `E1 + E2` checks that both are int. Correct.
- (C) A boolean expression `!E1` needs `E1.type = bool`. But the only rule that can make a leaf is $E\to ID$, which always gives int, and `!E1` itself gives bool only when `E1` was already bool. So no bool expression can ever be built, and a `bool` declaration is never used. Not usable.
- (A) False for the same reason: programs with `bool` variables are not checked correctly.
- (D) The actions are plain checks and assignments. There is no loop.

**Key idea:** an action that ignores the symbol table (here $E\to ID$ always gives int) cannot type-check variables of other types.

</details>
