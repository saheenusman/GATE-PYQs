# 2015 CS3 Q45: Policies that prevent deadlock

## Question

Consider the following policies for preventing deadlock in a system with mutually exclusive resources.

- I. Processes should acquire all their resources at the beginning of execution. If any resource is not available, all resources acquired so far are released
- II. The resources are numbered uniquely, and processes are allowed to request for resources only in increasing resource numbers
- III. The resources are numbered uniquely, and processes are allowed to request for resources only in decreasing resource numbers
- IV. The resources are numbered uniquely. A process is allowed to request only for a resource with resource number larger than its currently held resources

Which of the above policies can be used for preventing deadlock?

- (A) Any one of I and III but not II or IV
- (B) Any one of I, III, and IV but not II
- (C) Any one of II and III but not I or IV
- (D) Any one of I, II, III, and IV

<details class="success" markdown="1">
<summary>Answer</summary>

**D**

</details>

<details class="info" markdown="1">
<summary>Solution</summary>

A deadlock needs four conditions. Each policy breaks one of them.

- **I breaks hold-and-wait.** A process never holds some resources while waiting for others, because it takes everything at once or releases what it has.
- **II breaks circular wait.** With requests only in increasing order, a cycle of waiting processes would need resource numbers to increase all the way around the cycle, which is impossible.
- **III breaks circular wait too.** Decreasing order is the same idea with the order reversed.
- **IV breaks circular wait.** "Only a resource larger than any currently held" is the same as requesting in increasing order.

So any one of the four works: option (D).

(A), (B) and (C) wrongly exclude a policy that is valid. The direction of the global order does not matter, only that every process follows the same one.

**Key idea:** a fixed global ordering of resources (in either direction) prevents circular wait.

</details>
